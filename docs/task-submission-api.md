# Task submission API contract

The Task API is Steward's single server-side execution surface for `steward-run`, Burble,
the request portal, and scheduled service work. Its machine-readable contract is generated by
`steward_apiserver::ApiDoc`; the source annotations and response types live in
`crates/steward-apiserver/src/lib.rs` and `crates/steward-apiserver/src/tasks.rs`.

## Lifecycle

All routes require an HTTP bearer identity assertion. A submission also requires a
submitter-scoped `Idempotency-Key`.

| Method | Path | Success |
|---|---|---|
| `POST` | `/v1/tasks` | `201` when admitted without a hold; `202` when parked for approval |
| `PUT` | `/v1/tasks/{taskUid}/inputs` | `204`; body is `application/x-tar` |
| `POST` | `/v1/tasks/{taskUid}/execute` | `202`; desired execution is recorded durably |
| `GET` | `/v1/tasks/{taskUid}` | `200`; returns `TaskStatusResponse` |
| `GET` | `/v1/tasks/{taskUid}/outputs` | `200`; body is `application/x-tar` after success |
| `DELETE` | `/v1/tasks/{taskUid}` | `202`; desired cleanup is recorded durably |

`TaskStatusResponse.phase` is one of `submitted`, `parked`, `queued`, `running`,
`succeeded`, `failed`, or `cancelled`. `failureReason` is a safe server-generated reason and
is present only after failure. `deltas` carries the structured budget, TTL, model, or tool
counterexample when submission parks outside the service envelope. `finalized` is the cleanup
completion signal and is independent of execution phase.

## Tar paths and limits

The tar body is a workspace snapshot, not a second naming scheme:

- Every uploaded member name is workspace-relative, for example `in/payload.bin`.
- The task command runs with the extracted input root as its working directory.
- `STEWARD_OUTPUT_DIR` names a separate, initially empty collection root. Commands preserve
  declared output roots beneath it, for example `$STEWARD_OUTPUT_DIR/out/payload.bin`.
- Returned member names remain workspace-relative and include that declared root, for example
  `out/payload.bin`.
- Steward treats tar members and file contents as opaque. It does not rename, flatten, or
  interpret entries. As the submitting/extracting client, `steward-run` must continue to reject
  symlinks, absolute paths, and traversal before upload and after download.

The maximum raw HTTP input archive is **64 MiB (67,108,864 bytes)**. The maximum raw output
archive accepted from the sandbox is also **64 MiB (67,108,864 bytes)**. An oversized input is
`413 Payload Too Large`; oversized sandbox output fails the Task before output persistence.

## Production identity boundary

`KubernetesTaskIdentityResolver` sends the bearer assertion unchanged in a Kubernetes
`authentication.k8s.io/v1 TokenReview`. It requests the one audience configured by
`STEWARD_TASK_TOKEN_AUDIENCE`, and `task_identity_from_token_review` accepts exactly one
service group plus either an acting user or a task owner:

```text
agents.apelogic.ai/service-principal:steward-run
agents.apelogic.ai/acting-user:<corporate-email>
```

Pure service work uses the service group plus
`agents.apelogic.ai/task-owner:<corporate-email>` instead. Steward rejects missing, duplicate,
empty, or contradictory identity groups.

The supported production audience is **`steward-task-api`**. GitHub Actions must request its
OIDC token with `aud=steward-task-api`; the audience-aware TokenReview authenticator must verify
that claim and return `steward-task-api` in `status.audiences`.

There is currently **no component in this repository** that validates GitHub's OIDC issuer,
authorizes repository/workflow claims, resolves the GitHub actor to a corporate email, and
creates the two groups above. The E2E `TestTaskIdentities` resolver is deliberately only a test
fixture. Production therefore still requires an external Kubernetes structured JWT
authenticator or authentication webhook implementing that mapping. Kubernetes documents both
the audience intersection and group-bearing TokenReview response in its
[authentication reference](https://kubernetes.io/docs/reference/access-authn-authz/authentication/),
and GitHub documents custom OIDC audiences in its
[OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).

Until that mapper is deployed and tested with a real GitHub token, the GitHub production
identity path is a blocker; the Task API does not infer identity from unverified JWT claims.
